# План агентов: состав, порядок запуска, первые задачи

Документ для координатора: по одному треду на роль. Каждому агенту в первом сообщении передать: «Прочитай CLAUDE.md целиком и раздел своей роли в docs/AGENTS-PLAN.md; затем выполни первую задачу».

## Схема зависимостей

```
Волна 1 (сразу):        Фундамент ─────────────┐        Контент (параллельно, только по формату §6)
                              │ PR#1: каркас + course-schema + core
Волна 2 (после PR#1):   Бэкенд ──────┐          Приложение (на моках api-contract)
                              │ миграции + RLS + import-course
Волна 3 (после миграций): Наставник (функции ИИ)  → Приложение подключает реальные функции
Волна 4 (вертикальный срез MVP готов): QA и релиз
```

Критический путь до R1: Фундамент → Бэкенд → Наставник → интеграция в Приложении → QA. Контент модуля 1 должен быть готов к началу волны 3, чтобы Наставника было на чём проверять.

**Блокер до старта волны 1:** нужен репозиторий на GitHub (решение владельца №1). Без него «Фундамент» и «Контент» могут готовить работу локально, но не открывать PR.

## 1. Фундамент (архитектор платформы)

**Зона:** корень репозитория, `packages/core`, `packages/course-schema`, `packages/api-contract`, `tools/course-cli`, `.github/workflows`, `CLAUDE.md`, `README.md`.
**Зависит от:** репозитория. **Ждут его:** все.

**Первая задача (PR#1, «каркас»):**
1. Перенести в репозиторий `CLAUDE.md`, `docs/AGENTS-PLAN.md`, `docs/OWNER-DECISIONS.md`, `docs/decisions/0001-stack.md` и `docs/spec/pm-school-spec.md` из общей папки проекта.
2. Создать монорепо pnpm: корневые конфиги TS/ESLint/Prettier, пустой Expo-проект `apps/app` (Expo Router, NativeWind, запускается на вебе), заготовки `packages/*`, `supabase/` (`supabase init`), `courses/`, `evals/`.
3. Проверить связку импортов пакетов в Expo (Metro) и в Deno (Edge Functions), реализовать `pnpm sync:shared` (CLAUDE.md §4.3) или упростить через ADR.
4. CI: install, lint, typecheck, test, `course:validate`, проверка актуальности `_shared/vendor`.
5. Зафиксировать версии библиотек в ADR-0001.

**Вторая задача (PR#2–3):** `course-schema` (zod-схема §6, парсер папки, валидатор §6.4, CLI `course:validate`) и `core` (правила §7 с тестами на границы: 69/70, 49/50 ×3, 10/11 вопросов, ступени 1→4, грейды G0–G4 по манифесту PM). `api-contract`: схемы входа/выхода функций §9 и схема результата проверки.

## 2. Контент (методист курса)

**Зона:** `courses/`. Код не пишет.
**Зависит от:** формата курса (CLAUDE.md §6) — можно начинать сразу. Валидатором пользуется, как только «Фундамент» его смержит.

**Первая задача:** собрать `courses/pm-senior/` по спецификации:
1. `course.yaml` (правила и грейды из CLAUDE.md §6.2), `mentor.md` (системный промпт из спецификации §11, адаптированный под платформу: без правил, которые уже в коде).
2. Все 13 `module.yaml` и заготовки 81 урока со `status: draft` (ключ, название, пустой текст), чтобы карта курса была полной.
3. Модуль 1 полностью: развернуть сжатый контент спецификации §6 в 6 уроков (1–1,5 ч чтения каждый) с 3 вопросами самопроверки; задания `m01.theory` и `m01.case` из спецификации с критериями; `case.customer.md` (скрытые факты «Меридиана»: что знает каждый директор, где противоречия, как отвечать на конкретные вопросы); эталоны `*.reference.md`.

**Дальше:** модули 2–13 по одному PR на модуль; затем сквозной кейс и финальная защита (после решений владельца №5, №6).

**Особое правило:** эталоны и `*.customer.md` пишет так, чтобы они были сильнее среднего ответа, с цифрами и допущениями; это то, против чего ИИ сравнивает решения.

## 3. Бэкенд (Supabase)

**Зона:** `supabase/` (миграции, RLS, seed, pgTAP-тесты, `_shared/db`, функции `import-course`, `enroll`, `recompute-progress`), настройки Auth и Storage.
**Зависит от:** PR#1 Фундамента (каркас), `course-schema` для импорта. **Ждут его:** Наставник, Приложение (реальные данные).

**Первая задача:**
1. Миграции всех таблиц CLAUDE.md §8 с enum-типами и индексами.
2. Политики RLS §8.4 и pgTAP-тесты: ученик не видит чужие строки и `assignment_secrets`, не пишет в серверные таблицы.
3. Auth: вход по e-mail (magic link / код), профиль создаётся триггером.
4. Функции `import-course` (через `course-schema`) и `enroll`; `pnpm course:import` работает против локального Supabase; seed импортирует `courses/pm-senior`.
5. `_shared/db`: типизированный доступ к таблицам для функций Наставника (генерация типов `supabase gen types`).

## 4. Приложение (Expo: телефон и веб)

**Зона:** `apps/app`.
**Зависит от:** PR#1 Фундамента, `api-contract`. До готовности бэкенда работает на моках в `src/api/mocks` с данными модуля 1 из `courses/pm-senior`.

**Первая задача:**
1. Дизайн-система `src/ui`: типографика для длинного чтения, кнопки, карточки, бейджи статусов, тёмная тема. Читаемость текста на телефоне — главный приоритет.
2. Экраны MVP (функции 1–7 спецификации §10): вход; список курсов; карта курса (модули, статусы, блокировки, грейд); читалка урока + вопросы самопроверки + чат с наставником по теории; экран задания (условие, критерии, редактор Markdown с автосохранением черновика, история попыток, разбор с баллами); лестница подсказок; чат «заказчика» со счётчиком; эталон после зачёта; профиль и история грейдов; отчёт о применении.
3. Навигация и адаптивность: телефон (одна колонка), веб на широком экране (боковая карта курса + контент).

## 5. Наставник (ИИ)

**Зона:** функции `submit-attempt`, `request-hint`, `ask-customer`, `mentor-chat`, `reveal-reference`; `supabase/functions/_shared/ai` (клиент Claude, промпты, сборка контекста); `evals/`.
**Зависит от:** миграций Бэкенда, `core` и `api-contract`, контента модуля 1.

**Первая задача:**
1. ADR о доставке длинных ответов (стрим или Realtime, CLAUDE.md §9).
2. `_shared/ai`: клиент `@anthropic-ai/sdk`, модель `claude-opus-5-5` из `MENTOR_MODEL`, адаптивное мышление, effort по ролям (§7.5), структурированный вывод проверки, обработка refusal и сбоев, prompt caching.
3. Промпты ролей: проверка, подсказка (с отклонением слабой попытки и защитой от выуживания ответа), заказчик, теория, эталон со сравнением.
4. Функции по §9 с правилами из `core`.
5. `evals/m01`: 6–10 эталонных решений разного качества для заданий модуля 1 (слабое, «общие слова», пограничное 65–75, сильное) с ожидаемыми диапазонами баллов; скрипт ручного прогона. Цель: разброс оценки одного решения между прогонами не больше ±5 баллов, «общие слова» стабильно ниже 50.

## Как координатору вести агентов

- Один тред на роль; каждая задача агенту = ссылка на раздел этого плана + конкретный результат.
- Еженедельно (или по завершении волны) сверять журналы `docs/agents/*.md` и открытые ADR.
- Конфликт зон решает координатор; изменение контракта — только через ADR.
- Когда владелец принимает решение из `docs/OWNER-DECISIONS.md`, координатор переносит его в ADR или CLAUDE.md и уведомляет затронутые роли.
