# CLAUDE.md: единый источник правды для агентов проекта «Обучалка»

> Этот файл читает каждый агент перед началом любой работы. Если твоя задача противоречит этому файлу, остановись и напиши координатору; не отступай молча.
> Версия документа: 1.1 (17.11.2026). Владелец файла: агент «Фундамент» (см. §12). Остальные предлагают правки через координатора.

---

## 0. Как пользоваться этим файлом

1. Прочитай §1–§4 целиком, затем раздел своей роли в §12.
2. Перед правкой кода найди в §3 свою зону. Всё вне зоны только читаешь.
3. Термины употребляй строго по словарю §11 (в коде, UI, коммитах и сообщениях).
4. Любое решение, которое меняет контракт между зонами (схема БД, формат курса, API функций, правила обучения), фиксируй как ADR в `docs/decisions/` (§10.4).
5. Исходная постановка первого курса лежит в `docs/spec/pm-school-spec.md`. Если CLAUDE.md и спецификация расходятся, прав CLAUDE.md, а расхождение отмечай координатору.

## 1. Продукт

**Что строим.** Личную обучающую платформу: мобильное приложение (iOS, Android) и веб-версию с одной кодовой базой. В платформу загружаются **курсы**; ученик проходит их с **ИИ-наставником**, который проверяет задания по критериям, дозирует подсказки и играет роль «заказчика» в кейсах.

**Главный принцип: платформа, а не одна школа.** Школа «Путь к Senior PM» из спецификации это первый и эталонный курс (`courses/pm-senior/`). Всё, что в спецификации специфично для этого курса (проходной балл 70, 4 ступени подсказок, грейды G0–G4, лимит 10 уточняющих вопросов, правило «3 раза ниже 50»), в коде **не зашивается**, а задаётся в манифесте курса (§6.2). Код платформы реализует общий механизм, курс настраивает параметры.

**Пользователи.**
- *Ученик* (learner): проходит курсы. На старте это один человек, владелец проекта.
- *Автор* (author): загружает и обновляет курсы. На старте тот же человек.
- *Админ* (admin): служебная роль для обслуживания.
Модель данных с первого дня многопользовательская (у всего есть `user_id`), но UI регистрации для посторонних не делаем, пока владелец не решит иначе.

**Язык.** Интерфейс, контент курсов и общение наставника на русском. Строки UI выносим в словарь `apps/app/src/i18n/ru.ts`, чтобы позже добавить другие языки.

**MVP (релиз R1).** Полностью проходимый модуль 1 курса PM на вебе и Android:
вход → карта курса → чтение подмодулей 1.1–1.6 с вопросами самопроверки → вопросы наставнику по теории → задание 1.1 (записка) → проверка ИИ с баллами по критериям → лестница подсказок → кейс 1.2 «Меридиан» с чатом «заказчика» (счётчик 10) → эталон после зачёта → отчёт о применении → открытие модуля 2 и пересчёт грейда.

Вне MVP (R2+): загрузка курса zip-архивом из приложения, сквозной кейс, финальная защита, экспорт портфолио, прогноз сроков, режим «экзамен на модуль», iOS-сборка, офлайн-чтение.

## 2. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Язык | **TypeScript** (strict) везде | Один язык для приложения, бэкенда, схемы курса и тестов. Агентам проще, меньше стыков. |
| Приложение | **Expo** (React Native) + **Expo Router** + React Native Web | Одна кодовая база на iOS, Android и веб. Сборки в облаке (EAS), без своего Mac/Android Studio. |
| UI | **NativeWind** (Tailwind для RN) + свои компоненты в `src/ui` | Быстро, единообразно на всех платформах. Сторонние UI-киты не добавляем без ADR. |
| Markdown | `react-native-markdown-display` (теория, задания, разборы) | Весь контент курса в Markdown. |
| Данные на клиенте | **TanStack Query** + `@supabase/supabase-js` | Кэш, повторные запросы, офлайн-толерантность. |
| Бэкенд | **Supabase**: Postgres, Auth, Storage, Edge Functions (Deno) | Нет своего сервера для администрирования; авторизация и защита строк (RLS) из коробки; бесплатный тариф для одного ученика. |
| ИИ | **Claude API** (`@anthropic-ai/sdk`), вызывается **только** из Edge Functions | Ключ API никогда не попадает в клиент. Модель по умолчанию `claude-opus-5-5` (§7.5). |
| Валидация | **zod** | Одна схема для формата курса, контрактов API и ответов ИИ. |
| Монорепо | **pnpm workspaces**, Node 22 LTS | Простое и быстрое; Turborepo не вводим без нужды. |
| Тесты | Vitest (пакеты, приложение), `deno test` (функции), pgTAP (RLS и SQL), Playwright (веб e2e, с R1) | |
| CI | GitHub Actions | lint, typecheck, test, валидация курсов на каждый PR. |
| Доставка | Веб: статический экспорт Expo на хостинг (EAS Hosting или Cloudflare Pages, решает «QA и релиз» через ADR). Мобильные: EAS Build (Android APK для себя, iOS после решения владельца). | |

Версии библиотек фиксирует агент «Фундамент» при создании репозитория (последние стабильные на дату) и записывает в ADR-0001. Обновление мажорных версий только через ADR.

## 4. Общие соглашения по коду

### 4.1 Язык и стиль
- Идентификаторы, имена файлов, ветки, коммиты: **английский**.
- Комментарии в коде, документация, ADR, описания PR, тексты UI: **русский**.
- TypeScript `strict: true`, `noUncheckedIndexedAccess: true`. `any` запрещён; если неизбежен, `// eslint-disable-next-line` с причиной.
- Форматирование Prettier, линт ESLint (конфиги в корне). Код без ошибок линта и типов не мержится.
- Функции маленькие, без побочных эффектов там, где это возможно. Бизнес-правила только в `packages/core` (§7), не в экранах и не в SQL.

### 4.2 Именование
| Что | Стиль | Пример |
|---|---|---|
| Файлы TS/TSX | kebab-case | `hint-ladder.ts`, `lesson-screen.tsx` |
| React-компоненты | PascalCase | `LessonScreen` |
| Функции, переменные | camelCase | `computeModuleStates` |
| Типы, интерфейсы, zod-схемы | PascalCase; схема с суффиксом `Schema` | `Submission`, `SubmissionSchema` |
| Константы | UPPER_SNAKE | `MAX_ATTEMPT_LENGTH` |
| Таблицы и колонки БД | snake_case, таблицы во множественном числе | `hint_requests.attempt_text` |
| Enum в БД | snake_case значения | `needs_rework` |
| Edge Functions | kebab-case, глагол-объект | `submit-attempt` |
| Ключи контента | см. §6.3 | `m01`, `1.1`, `m01.case` |

### 4.3 Импорты пакетов
Пакеты `packages/*` потребляются **как исходники** (без сборки). Внутри пакетов относительные импорты пишутся **с расширением `.ts`** (нужно для Deno). Внешние зависимости пакетов: только `zod`. Скрипт `pnpm sync:shared` копирует `packages/core`, `packages/course-schema`, `packages/api-contract` в `supabase/functions/_shared/vendor/`; CI проверяет, что копия актуальна. Проверено при создании репозитория: прямой импорт при деплое ненадёжен, схема с копией остаётся (ADR-0002). В функциях импортируем `@obuchalka/core`, `@obuchalka/course-schema`, `@obuchalka/api-contract` через карту в `supabase/functions/deno.json`.

### 4.7 Зависимости приложения
Пакеты в `apps/app` ставятся командой `npx expo install <пакет>` из папки `apps/app` (подбирает версии под Expo SDK). Если облачная песочница не пускает к API Expo, добавьте `EXPO_OFFLINE=1`. Версии зафиксированы в ADR-0001.

### 4.4 Ошибки и логирование
- Edge Functions возвращают ошибки в едином формате из `api-contract`: `{ error: { code: string, message: string } }`, где `message` по-русски для показа пользователю, `code` в snake_case для логики (`attempt_too_short`, `hint_step_locked`, `question_limit_reached`, `module_locked`, `ai_unavailable`).
- Никаких секретов, текстов решений или личных данных в логах. Логируем id и коды.

### 4.5 Тесты
- `packages/core`: покрытие правил 100% веток; каждое правило из §7 имеет хотя бы один тест на граничное значение (69/70, 49/50, 10-й и 11-й вопрос).
- Миграции: pgTAP-тест на каждую политику RLS (ученик не видит чужое и не видит `assignment_secrets`).
- Функции ИИ: юнит-тесты на сборку промпта и разбор ответа с подменённым клиентом Claude; живые вызовы только в `evals/`, вручную.
- Приложение: тесты на хуки и форматирование; e2e (Playwright, веб) на путь MVP с R1.

### 4.6 Секреты и окружения
- Секреты только в `.env.local` (в `.gitignore`) и в секретах Supabase/EAS/GitHub. В репозитории только `.env.example` с пустыми значениями.
- Клиент знает лишь `EXPO_PUBLIC_SUPABASE_URL` и `EXPO_PUBLIC_SUPABASE_ANON_KEY`.
- `ANTHROPIC_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY` есть только у Edge Functions.
- Окружения: `local` (supabase start), `prod`. Отдельный staging не заводим до R2.

## 5. Git: ветки, коммиты, PR

- Основная ветка `main`, защищена: только через PR с зелёным CI. Прямые пуши в `main` запрещены всем агентам.
- Ветка: `<role>/<short-kebab-description>`, роль из §12: `foundation/`, `backend/`, `mentor/`, `app/`, `content/`, `qa/`. Пример: `backend/rls-submissions`. Если среда агента сама назначает имя ветки (например, `claude/...` в облачных сессиях), используй его, а роль укажи в заголовке PR: `[backend] RLS для submissions`.
- Коммиты: **Conventional Commits** на английском, scope = зона: `feat(core): add hint ladder gating`, `fix(app): lesson screen scroll on web`, `content(pm-senior): module 1 lessons 1.1-1.3`, `chore(ci): cache pnpm store`. Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `content`.
- PR маленькие (ориентир до 400 строк кода без учёта контента и lock-файлов), одна задача на PR. Описание на русском: что сделано, зачем, как проверить, какие зоны затронуты, ссылки на ADR.
- Перед PR: `pnpm lint && pnpm typecheck && pnpm test` (и `pnpm course:validate`, если трогал курсы).
- Перед началом работы и перед PR делай `git fetch origin main` и rebase на свежий `main`. Конфликт в чужой зоне не разрешай сам: напиши владельцу.
- Мерж в `main` выполняет владелец репозитория или координатор по его поручению. Агент не мержит свои PR сам, если ему это явно не поручено.
- Миграции БД: только новые файлы `supabase/migrations/<timestamp>_<name>.sql`; уже смерженную миграцию не правим.

## 6. Формат загружаемого курса

Курс это папка (в репозитории `courses/<slug>/`, позже zip-архив той же структуры). Валидатор: `pnpm course:validate courses/<slug>`. Импорт в БД: `pnpm course:import courses/<slug>` (CLI вызывает функцию `import-course`). Источник правды формата: zod-схема в `packages/course-schema`; этот раздел её описывает, и при расхождении схема обновляется под этот раздел через ADR.

### 6.1 Структура папки

```
courses/pm-senior/
├─ course.yaml                     # манифест: метаданные, правила, грейды
├─ mentor.md                       # персона наставника (системный промпт курса)
├─ modules/
│  └─ m01-role-of-pm/
│     ├─ module.yaml               # key, title, summary
│     ├─ lessons/
│     │  ├─ 1.1-project-product-program.md
│     │  └─ ...
│     └─ assignments/
│        ├─ theory.md              # задание: условие + критерии во frontmatter
│        ├─ theory.reference.md    # СЕКРЕТ: эталон (показ только после зачёта)
│        ├─ case.md
│        ├─ case.customer.md       # СЕКРЕТ: скрытые факты для роли «заказчика»
│        ├─ case.reference.md      # СЕКРЕТ
│        └─ case.grader.md         # СЕКРЕТ, необязательный: заметки для проверяющего
├─ project/                        # сквозной кейс (необязателен для курса)
│  ├─ project.yaml
│  └─ stages/s1-*.md (+ .customer.md, .reference.md)
└─ final/                          # финальная защита (необязательна)
   └─ defense.md (+ секреты)
```

Файлы `*.customer.md`, `*.reference.md`, `*.grader.md` при импорте попадают в таблицу `assignment_secrets` и **никогда** не отдаются клиенту напрямую (§8).

### 6.2 `course.yaml`

```yaml
format_version: 1
slug: pm-senior
version: 0.1.0                 # semver контента; импорт новой версии не ломает прогресс (§8.3)
title: "Путь к Senior PM"
description: "Школа управления IT-проектами: от стажёра до Senior PM."
language: ru
estimated_hours: [350, 450]
disclaimer: >
  Школа не образовательная организация и документов не выдаёт. Грейды действуют только внутри программы.

rules:
  pass_score: 70                     # минимальный балл зачёта задания (0–100)
  module_gate: all_assignments_passed  # all_assignments_passed | none
  fail_streak:                       # серия слабых попыток
    below: 50
    count: 3
    action: return_to_theory         # эталон не выдаётся, теория модуля снова «к прочтению»
  reference_after_pass: true         # эталон только после зачёта
  clarifying_questions_default: 10   # лимит вопросов «заказчику» в кейсах
  hint_ladder:
    enabled: true
    min_attempt_chars: 300           # короче — попытка не принимается к подсказке
    steps:
      - { key: nudge,     title: "Вопрос-наводка" }
      - { key: direction, title: "Направление" }
      - { key: logic_gap, title: "Разбор логики" }
      - { key: analogy,   title: "Пример на похожей задаче" }
  self_check_per_lesson: 3
  exam_mode_allowed: true            # «экзамен на модуль»: теорию можно пропустить
  application_report: required       # required | optional | off; после зачёта модуля
  theory_questions_unlimited: true   # уточнения по теории без ограничений

grades:                              # по порядку; каждый следующий требует выполнения предыдущих
  - key: G0
    title: "Стажёр"
    conditions: []
  - key: G1
    title: "Junior PM"
    conditions:
      - { type: modules_passed, modules: [m01, m02, m03] }
  - key: G2
    title: "Middle PM"
    conditions:
      - { type: modules_passed, modules: [m04, m05, m06] }
      - { type: assignment_min_score, assignment: project.s1, min: 75 }
  - key: G3
    title: "Lead PM"
    conditions:
      - { type: modules_passed, modules: [m07, m08, m09, m10] }
      - { type: average_score_min, modules: [m07, m08, m09, m10], min: 78 }
  - key: G4
    title: "Senior PM"
    conditions:
      - { type: modules_passed, modules: [m11, m12, m13] }
      - { type: assignment_min_score, assignment: final, min: 85 }

grade_loss:                          # необязательно; точная формулировка — решение владельца
  - { type: project_stage_below, min: 60, effect: drop_one_level }
```

Типы условий грейда (расширяются только через ADR): `modules_passed`, `assignment_min_score`, `average_score_min` (среднее лучших зачётных баллов по всем заданиям перечисленных модулей).

### 6.3 Ключи и frontmatter

**Ключи** уникальны в пределах курса и стабильны между версиями (по ним переносится прогресс):
- модуль: `m01`…`m13` (в `module.yaml`);
- подмодуль (урок): `1.1`, `10.7` (во frontmatter);
- задание: `<module>.<name>`: `m01.theory`, `m01.case`; сквозной кейс `project.s1`…; финал `final`.

**Урок** (`lessons/1.1-*.md`):
```markdown
---
key: "1.1"
title: "Проект, продукт, программа, портфель, эксплуатация"
est_minutes: 60
status: ready            # draft | ready; draft не показывается ученику
self_check:
  - "Чем проект отличается от продукта с точки зрения владения после запуска?"
  - "..."
  - "..."
---
Текст теории в Markdown. Заголовки с ##. Таблицы, списки, цитаты допустимы. Без HTML.
```

**Задание** (`assignments/case.md`):
```markdown
---
key: m01.case
kind: case               # theory | case | project_stage | final
title: "Платформа «Меридиан»"
status: ready
pass_score: 70           # необязательно, иначе rules.pass_score
clarifying_questions: 10 # только для case/project_stage; иначе rules.clarifying_questions_default
expected_volume: "до 5 страниц плюс приложения"
estimated_hours: [8, 15]
criteria:                # сумма весов строго 100
  - { key: diagnosis,     title: "Диагностика и гипотезы",                           weight: 20 }
  - { key: estimate,      title: "Реалистичность оценки и видимость допущений",      weight: 20 }
  - { key: scenarios,     title: "Проработка сценариев и обоснованность выбора",     weight: 20 }
  - { key: governance,    title: "Управленческое решение",                           weight: 15 }
  - { key: communication, title: "Коммуникация и работа с конфликтом интересов",     weight: 15 }
  - { key: plan30,        title: "Практичность плана 30 дней",                       weight: 10 }
---
Условие задания: вводные и «что сдать».
```

Секретные файлы содержат только Markdown, без frontmatter. Файл `*.customer.md` описывает, что «заказчик» знает и чего не знает, какие противоречия заложены и как отвечать на вопросы, не раскрывая лишнего.

### 6.4 Правила валидации (валидатор обязан проверять)
- уникальность ключей; ссылки грейдов указывают на существующие модули и задания;
- сумма весов критериев = 100; `pass_score` в 0–100;
- у задания `kind: case` есть `*.customer.md`; у каждого задания есть `*.reference.md` при `reference_after_pass: true` (для `status: draft` это предупреждение, не ошибка);
- у урока ровно `rules.self_check_per_lesson` вопросов (для `draft` предупреждение);
- в Markdown нет HTML и внешних скриптов; изображения только из папки курса `assets/`.

## 7. Ключевая бизнес-логика

Вся логика ниже живёт в `packages/core` как **чистые функции** (вход: снимок состояния и правила курса, выход: решение). Edge Functions вызывают их и сохраняют результат; приложение вызывает их только для подсказок в UI (например, серым показать, что модуль закрыт), но **авторитетно решает сервер**.

### 7.1 Открытие модулей
- Модуль 1 открыт при записи на курс.
- При `module_gate: all_assignments_passed` модуль N+1 открывается, когда все задания модуля N с `kind` theory/case имеют статус `passed`.
- Режим «экзамен на модуль» (если разрешён): ученик может отметить открытый модуль как экзаменационный; уроки помечаются «пропущены», задания доступны сразу. Модуль считается зачтённым так же, по заданиям.
- Задания модуля доступны после того, как все уроки модуля отмечены прочитанными (или включён экзаменационный режим).

### 7.2 Попытки и оценка
- Каждая сдача решения создаёт `submission` с номером попытки `attempt_no` (1, 2, 3…).
- Оценка ставит балл по каждому критерию от 0 до веса критерия; итог = сумма (0–100), целое число.
- Итог ≥ `pass_score` → `passed`, иначе `needs_rework`. После `passed` новые попытки по заданию не принимаются.
- **Серия слабых попыток:** если последние `fail_streak.count` подряд попыток по заданию < `fail_streak.below`, то эталон для задания закрывается навсегда (`reference_blocked = true`), а уроки модуля возвращаются в статус «к повторению»; новая попытка возможна после повторного прочтения уроков модуля.
- Общие фразы без цифр, допущений и обоснования оцениваются нулём по соответствующему критерию (правило наставника, §7.5).

### 7.3 Лестница подсказок
- Ступени 1…N из `rules.hint_ladder.steps`. Запрос ступени k+1 возможен только после того, как на ступени k ученик отправил попытку (черновик) и подсказка k выдана.
- Попытка для подсказки: текст ≥ `min_attempt_chars` и содержит, что понято, что пробовал, где упёрся. Длину проверяет `core`; содержательность проверяет ИИ, который вправе отклонить попытку (`accepted = false` с причиной), и тогда ступень не расходуется.
- После зачёта задания подсказки по нему не нужны и недоступны.
- Если запрос по сути просит готовый ответ, наставник говорит об этом и даёт менее прямую подсказку той же ступени.

### 7.4 Уточняющие вопросы «заказчику»
- Только для `case` и `project_stage`. Лимит из задания или правил курса.
- Каждый вопрос учитывается сразу при отправке; на 11-й (при лимите 10) сервер возвращает `question_limit_reached`.
- «Заказчик» отвечает только на конкретный вопрос, опираясь на `*.customer.md`, не подсказывает, о чём стоило спросить. Вопросы и ответы прикладываются к контексту проверки решения (качество вопросов оценивается).

### 7.5 ИИ-наставник (правила для зоны «Наставник»)
- Модель по умолчанию `claude-opus-5-5`, задаётся переменной `MENTOR_MODEL`. Адаптивное мышление, `output_config.effort`: `high` для проверки решений, `medium` для подсказок и чата, `low` для ответов «заказчика». Длинные ответы через стриминг.
- Проверка возвращает **структурированный** результат (`output_config.format` по zod-схеме из `api-contract`): баллы по каждому критерию с обоснованием, итог, разбор пробелов, при зачёте сравнение с эталоном. Итог пересчитывается в коде как сумма баллов, а не берётся у модели на веру.
- Системный промпт = общие правила платформы (`_shared/ai/prompts/platform.md`) + `mentor.md` курса + контекст роли (проверка / подсказка / заказчик / теория). Эталон и `*.grader.md` попадают в контекст проверки, но в ответе ученику при незачёте эталон не цитируется.
- Обрабатывать `stop_reason: refusal` и сбои API: попытка получает статус `review_failed`, ученик видит «проверка не удалась, повторите», счётчики не расходуются.
- Стабильные части промпта (правила, персона, урок, задание) идут первыми и кэшируются (prompt caching).

### 7.6 Грейд
- Пересчитывается сервером после каждого изменения статуса задания: первый грейд с конца списка, условия которого и всех предыдущих выполнены.
- Потеря грейда по правилам `grade_loss`. Каждое изменение пишется в `grade_events` с основанием.
- В UI рядом с грейдом всегда показывается `disclaimer` курса.

### 7.7 Прочее
- Отчёт о применении: при `application_report: required` после зачёта модуля следующий модуль открыт, но на карте висит напоминание, пока отчёт не сдан (не блокирует; см. решения владельца).
- Учёт времени: приложение пишет время чтения урока и работы в редакторе в `time_logs`; прогноз сроков (R2) считает по факту.

## 8. Модель данных (Supabase Postgres)

Схема делится на **контент** (импортируется, ученику только чтение) и **прогресс** (пишется сервером от имени ученика). Все таблицы с `id uuid default gen_random_uuid()`, `created_at timestamptz default now()`. RLS включён на всех таблицах.

### 8.1 Контент
| Таблица | Ключевые поля |
|---|---|
| `courses` | slug (unique), title, description, language, current_version_id |
| `course_versions` | course_id, version (semver), manifest jsonb (rules, grades, grade_loss, disclaimer), mentor_md, source_hash, status (`draft`/`published`), imported_by |
| `modules` | course_version_id, key, position, title, summary |
| `lessons` | module_id, key, position, title, body_md, est_minutes, self_check jsonb (массив строк), status |
| `assignments` | course_version_id, module_id (null для project/final), key, kind, title, body_md, criteria jsonb, pass_score, clarifying_questions_limit, expected_volume, status |
| `assignment_secrets` | assignment_id (PK), customer_md, reference_md, grader_md. **Нет политик для клиента: читают только функции с service role.** |
| `course_imports` | course_id, version, status (`ok`/`failed`), errors jsonb, warnings jsonb, imported_by |

### 8.2 Прогресс ученика
| Таблица | Ключевые поля |
|---|---|
| `profiles` | user_id (PK, = auth.users.id), display_name, role (`learner`/`author`/`admin`), timezone |
| `enrollments` | user_id, course_id, course_version_id, started_at, weekly_hours, real_work_context, current_grade, status (`active`/`paused`/`completed`) |
| `module_states` | enrollment_id, module_key, status (`locked`/`open`/`passed`), exam_mode bool, passed_at |
| `lesson_progress` | enrollment_id, lesson_key, status (`not_started`/`read`/`review_required`), read_at, self_check_answers jsonb (необязательно) |
| `submissions` | enrollment_id, assignment_key, attempt_no, body_md, attachments jsonb, status (`pending`/`reviewing`/`passed`/`needs_rework`/`review_failed`), total_score, criterion_scores jsonb, review_md, model, reviewed_at |
| `assignment_states` | enrollment_id, assignment_key, status (`locked`/`open`/`passed`), best_score, attempts_count, weak_streak, reference_blocked bool, reference_revealed_at |
| `clarifying_questions` | enrollment_id, assignment_key, n, question, answer, model |
| `hint_requests` | enrollment_id, assignment_key, step, attempt_text, accepted bool, rejection_reason, hint_md, model |
| `mentor_messages` | enrollment_id, context_type (`lesson`/`assignment`/`general`), context_key, role (`learner`/`mentor`), content_md |
| `grade_events` | enrollment_id, from_grade, to_grade, reason jsonb |
| `application_reports` | enrollment_id, module_key, real_task, tool_applied, what_worked, what_failed |
| `time_logs` | enrollment_id, day date, minutes, source (`lesson`/`assignment`/`manual`) |

Прогресс ссылается на контент по **ключам** (`module_key`, `lesson_key`, `assignment_key`), а не по uuid, чтобы при импорте новой версии курса прогресс сохранялся.

### 8.3 Версии курса
- Импорт новой версии создаёт новую `course_versions` и делает её текущей. Записи учеников переходят на неё автоматически; прогресс по ключам сохраняется. Удалённые ключи помечаются в `course_imports.warnings`, их прогресс не удаляется.
- Удаление задания или смену его критериев после зачёта валидатор помечает предупреждением: старые баллы не пересчитываются.

### 8.4 Доступ (RLS)
- Ученик читает контент опубликованных версий курсов, на которые записан (кроме `assignment_secrets`), и **только свои** строки прогресса.
- Ученик **не пишет** напрямую в `submissions`, `assignment_states`, `module_states`, `grade_events`, `hint_requests`, `clarifying_questions`: только через Edge Functions. Напрямую пишет лишь `lesson_progress` (отметка «прочитано»), `application_reports`, `time_logs`, `mentor_messages` с ролью `learner`, поля профиля и `enrollments.weekly_hours/real_work_context`.
- Автор импортирует курсы через `import-course` (проверка роли в функции).
- Вложения решений в Storage: бакет `submissions`, путь `<user_id>/<assignment_key>/<file>`, доступ только владельцу и функциям.

## 9. API: Edge Functions

Контракты (zod) лежат в `packages/api-contract`. Все функции требуют JWT пользователя, кроме служебных. Ответ всегда JSON, ошибки по §4.4.

| Функция | Вход | Что делает |
|---|---|---|
| `import-course` | zip или дерево файлов курса | валидирует (`course-schema`), пишет версию, секреты, отчёт импорта; роль `author` |
| `enroll` | course_slug, weekly_hours? | запись на курс, начальные `module_states`, грейд G0 |
| `submit-attempt` | assignment_key, body_md, attachments | проверки `core` (доступ, не зачтено) → проверка ИИ → `submissions`, `assignment_states`, модули, грейд |
| `request-hint` | assignment_key, step, attempt_text | проверки лестницы → ИИ (принять попытку? подсказка) → `hint_requests` |
| `ask-customer` | assignment_key, question | счётчик → ИИ в роли заказчика → `clarifying_questions` |
| `mentor-chat` | context_type, context_key, message | вопросы по теории и условиям без ограничений, без готовых решений |
| `reveal-reference` | assignment_key | только при `passed` и не `reference_blocked` → эталон + сравнение с лучшей попыткой |
| `recompute-progress` | enrollment_id | служебная: пересчёт состояний и грейда (после импорта новой версии) |

Длинные ответы ИИ (`submit-attempt`, `mentor-chat`) отдаются клиенту стримом (SSE) или по схеме «создали запись → клиент подписан на изменения (Supabase Realtime)». Выбор фиксирует «Наставник» в ADR до реализации.

## 10. Координация агентов

### 10.1 Роли и иерархия
- **Человек (владелец)** принимает продуктовые решения и решения, которые нельзя отменить (публикация в сторах, оплаты, удаление данных). Список открытых решений: `docs/OWNER-DECISIONS.md`.
- **Координатор** ведёт план, заводит задачи агентам, разрешает конфликты между зонами, передаёт решения владельца.
- **Агенты ролей** (§12) работают каждый в своей зоне, в своей ветке.

### 10.2 Порядок работы агента над задачей
1. Прочитать CLAUDE.md, свою роль, последние ADR и свой журнал `docs/agents/<role>.md`.
2. Свериться, не трогает ли задача чужие зоны или контракты. Если трогает — сначала согласовать (§3).
3. Работать в ветке `<role>/...`, маленькими PR.
4. После PR: дописать в `docs/agents/<role>.md` 3–5 строк: что сделано, что дальше, что блокирует, какие договорённости приняты.
5. Сообщить координатору результат одной фразой со ссылкой на PR. Если работу ждёт другая роль, сообщить и ей.

### 10.3 Чего нельзя делать никому
- Пушить в `main`, переписывать историю чужих веток, мержить свой PR без поручения.
- Менять смерженные миграции, `docs/spec/`, чужие зоны (кроме §3 п.1).
- Менять правила обучения (§7) или формат курса (§6) без ADR и согласования с координатором.
- Класть секреты и ключи в репозиторий, логи, сообщения.
- Добавлять платные сервисы, новые внешние зависимости крупнее утилиты, аналитику и трекинг без ADR; платные — только с решения владельца.
- Отключать, пропускать или ослаблять тесты, чтобы CI стал зелёным.
- Выдумывать требования: если в спецификации пробел, спросить координатора; до ответа сделать по наиболее вероятному прочтению и записать допущение в PR.

### 10.4 Как фиксировать решения (ADR)
Файл `docs/decisions/NNNN-kebab-title.md`, номер следующий по порядку (перед созданием сделай `git fetch` и проверь занятые номера):
```markdown
# NNNN. Заголовок
Статус: предложено | принято | заменено NNNN
Дата: ГГГГ-ММ-ДД · Автор: <роль>
## Контекст
## Решение
## Последствия (что меняется для других зон)
```
ADR, меняющий контракт, считается принятым после подтверждения координатора. После принятия автор обновляет затронутые разделы CLAUDE.md (через «Фундамент», если это не он).

### 10.5 Определение «готово»
Задача готова, когда: код в PR, CI зелёный, есть тесты по §4.5, обновлены документация и журнал роли, затронутые владельцы зон уведомлены.
